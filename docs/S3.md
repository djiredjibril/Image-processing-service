# Stockage objet S3 : comprendre, utiliser, et où il sert dans ce projet

> Guide d'apprentissage, comme `docs/REDIS.md` et `docs/BULLMQ.md`. Il part de zéro, puis montre comment le stockage S3
> est branché dans *Image Processing Service* (phase 5).

---

## 1. Le problème : pourquoi quitter le disque local ?

Jusqu'ici, les images sont des fichiers dans `apps/api/storage/`. C'est simple, mais :

1. **Un seul serveur.** Si l'API tourne sur deux machines, ou si le worker (phase 4) tourne ailleurs que l'API, ils ne voient
   pas le même disque : une image envoyée sur la machine A est introuvable sur la machine B.
2. **Le disque est lié au serveur.** Si on remplace la machine, les fichiers partent avec elle.
3. **Capacité et durabilité limitées** à un disque (pas de réplication).

Le **stockage objet** répond à cela : un service réseau, partagé, où l'on dépose et récupère des fichiers par leur **clé**.
« S3 » (Simple Storage Service, d'Amazon) est devenu **l'API standard** du stockage objet : beaucoup de produits
l'imitent (**SeaweedFS**, Garage, MinIO, Cloudflare R2, Scaleway...). Coder contre l'API S3, c'est ne pas dépendre d'un fournisseur.

## 2. Le vocabulaire

| Terme | Sens | Dans le projet |
|---|---|---|
| **Objet** | Un fichier + ses métadonnées (type MIME, taille, ETag) | une image |
| **Bucket** | Un « conteneur » d'objets, de nom unique | `imageservice-dev`, `imageservice-test` |
| **Clé** (*key*) | Le nom de l'objet dans le bucket. Pas de vrais dossiers : `originals/abc.png` est **une seule chaîne** | `StorageKey` (`originals/<uuid>.png`, `derived/<uuid>.webp`) |
| **Endpoint** | L'adresse du service S3 | `http://localhost:8333` (SeaweedFS) |
| **Access key / secret** | Identifiants de l'application | `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` |
| **Path-style** | Adresse `http://hôte/bucket/clé` (vs `http://bucket.hôte/clé`) | `S3_FORCE_PATH_STYLE=true` |
| **ETag** | Empreinte du contenu, renvoyée par le serveur | non utilisée ici |

Les opérations S3 utilisées : `PutObject` (écrire), `GetObject` (lire, en flux), `HeadObject` (existe ? sans transférer le
contenu), `DeleteObject`, `HeadBucket`/`CreateBucket` (au démarrage).

## 3. Où dans le code ?

```
docker-compose.yml, docker/seaweedfs-s3.json     SeaweedFS (port 8333) et son compte de développement
apps/api/src/
  domain/ports/file-storage.ts                   IFileStorage : put, get, delete, exists (INCHANGÉ depuis la phase 1)
  infrastructure/storage/
    local-file-storage.ts                        implémentation disque
    s3-file-storage.ts                           implémentation S3 (SDK @aws-sdk/client-s3) + ensureBucket
    create-file-storage.ts                       choisit local ou S3 selon STORAGE_DRIVER (API ET worker)
  infrastructure/config/config.ts                variables STORAGE_DRIVER, S3_*
```

Le gain de la Clean Architecture se voit ici : **aucun use case, aucune route n'a changé**. Ils parlaient déjà à `IFileStorage`.
Il a suffi d'écrire une seconde implémentation et de choisir laquelle brancher dans la composition root.

## 4. Les décisions de conception (et pourquoi)

### 4.1 Un contrat, deux implémentations, les mêmes tests
`tests/helpers/file-storage-contract.ts` décrit le comportement attendu de **tout** `IFileStorage` (octets identiques, fichier
absent → `null`, `delete` idempotent, original immuable, écriture simultanée atomique...). Il est exécuté contre le disque local
**et** contre un vrai SeaweedFS : si les deux passent, on peut les échanger sans surprise.

### 4.2 Immutabilité garantie par le serveur : `If-None-Match: *`
Un original ne doit jamais être écrasé. Sur disque, on ouvre avec le drapeau `wx` (« crée, échoue si ça existe »). Sur S3, on envoie
`If-None-Match: *` : le serveur répond **412 Precondition Failed** si la clé existe. C'est **atomique** : l'alternative « vérifier
avec `exists` puis écrire » laisserait une fenêtre où deux écritures simultanées passeraient toutes les deux (*race condition*).
Test : 5 `put` simultanés sur la même clé, un seul réussit.

### 4.3 Lecture en flux
`GetObject` renvoie un flux Node : l'image n'est pas chargée entièrement en mémoire pour être servie. Le flux doit être
consommé ou détruit (sinon la connexion réseau reste ouverte) : les routes utilisent `pipeline`, qui s'en charge.

### 4.4 `Content-Type` posé à l'écriture
Chaque objet reçoit son type MIME (`image/png`, `image/webp`...) déduit de l'extension de la clé (générée par le serveur, jamais
fournie par l'utilisateur). Utile pour les URLs présignées : le navigateur affiche l'image au lieu de la télécharger.

### 4.5 Le stockage est vital : fail-closed
Contrairement au cache (fail-open), sans stockage l'application ne peut rien faire d'utile. Au démarrage, `createFileStorage`
vérifie le bucket (le crée au besoin, **10 essais d'1 s** car S3 peut démarrer en même temps que l'API) et **refuse de démarrer** s'il
reste injoignable. En cours de route, une panne remonte en erreur 500 (« erreur inattendue » du middleware global).

### 4.6 L'API et le worker partagent le même stockage
`main.ts` et `worker.ts` appellent la même fabrique `createFileStorage(config)` : ils ne peuvent pas utiliser deux stockages
différents. C'est exactement ce que le disque local ne permettait pas (un worker sur une autre machine).

### 4.7 Les clés sont les mêmes qu'avant
`originals/<uuid>.<ext>` : la table `images.storage_key` n'a pas changé. Passer du disque à S3 = copier le dossier `storage/` dans le
bucket **en conservant les clés** (ex. `aws s3 sync storage/ s3://imageservice-dev --endpoint-url http://localhost:8333` avec la CLI AWS,
ou le client `mc`). Ce projet ne fournit pas de script de migration (hors périmètre) ; en développement, repartir de zéro suffit.

## 5. Les URLs présignées

### 5.1 Le principe
`GET /images/:id` fait passer **chaque octet par l'API** : pour 1000 utilisateurs qui regardent des images de 5 Mo, c'est l'API qui porte cette bande passante.
Une **URL présignée** inverse cela : l'API ne fait que l'**autorisation** (« cet utilisateur a-t-il le droit ? »), puis délivre une URL de courte durée
vers le stockage, et le navigateur télécharge **directement** depuis S3.

```
client ──GET /images/:id/url (jeton)──► API : propriétaire ? fichier présent ? ─► calcule la signature (local, sans réseau)
        ◄── { url, expiresInSeconds, expiresAt }
client ──GET <url> (AUCUN jeton)──────► stockage S3 : signature valide ? pas expirée ? ─► les octets
```

### 5.2 Comment ça marche (SigV4)
L'URL contient dans sa chaîne de requête : l'algorithme (`X-Amz-Algorithm`), l'identifiant de l'application (`X-Amz-Credential`), la date (`X-Amz-Date`),
la durée (`X-Amz-Expires`) et une **signature** (`X-Amz-Signature`) = HMAC-SHA256 calculé avec le **secret** (qui, lui, ne quitte jamais l'API) sur
l'hôte, le chemin, la clé et ces paramètres. Le stockage refait le même calcul : si **un seul caractère** de l'URL a changé (clé, durée, hôte), la signature ne
correspond plus → `403`. Et après `X-Amz-Expires` secondes → `403`. La signature est calculée **localement** : aucun appel réseau, donc aucun risque de panne du stockage à
cette étape.

### 5.3 Où dans le code ?
```
domain/ports/file-url-signer.ts                 IFileUrlSigner : presignGet(key, ttlSeconds)
infrastructure/storage/s3-file-url-signer.ts    implémentation (getSignedUrl du SDK)
application/use-cases/get-image-url.ts          GetImageUrl : autorisation, fichier présent, signature
infrastructure/http/routes/get-image-url-route.ts   GET /images/:id/url
```

### 5.4 Les décisions de conception
1. **Autoriser d'abord, signer ensuite.** Image d'un autre utilisateur : `404` (jamais 403), **avant** de regarder si le stockage sait signer.
2. **Une URL est une permission portée par l'URL elle-même** (*bearer capability*) : quiconque la possède peut lire le fichier jusqu'à l'expiration. D'où : durée courte
   (`PRESIGNED_URL_TTL_SECONDS`, 300 s par défaut, 7 jours au maximum, limite de SigV4), jamais journalisée, réponse en `Cache-Control: no-store`.
3. **Disque local : `501 Not Implemented`.** Le disque n'a pas d'adresse réseau ; c'est l'API qui sert ses fichiers (`GET /images/:id`). Le port est optionnel (signeur `null`).
4. **L'hôte fait partie de la signature.** On ne peut pas fabriquer l'URL avec un hôte interne puis le « corriger » : il faut signer avec l'adresse que le navigateur utilisera.
   D'où `S3_PUBLIC_ENDPOINT` (défaut `S3_ENDPOINT`) et un second client S3 réservé à la signature (ex. API dans Docker qui joint `http://seaweedfs:8333`, navigateur qui voit `http://localhost:8333`).
5. **Fichier absent : `404`.** Une requête `HEAD` vérifie que l'objet existe avant de signer, pour ne pas distribuer une URL qui mène à un 404.
6. **Aucune modification de `GET /images/:id`** : il reste disponible et authentifié (utile avec le disque local, ou pour un client qui ne veut pas parler au stockage).

### 5.5 Limites à connaître
- Une URL délivrée ne peut pas être **révoquée** avant son expiration : si on supprime l'image, l'URL ne marche plus (l'objet n'existe plus), mais si on retire le droit à l'utilisateur, elle reste valable jusqu'au bout. D'où une durée courte.
- Pour une page web qui ne ferait que `<img src="<url>">`, aucune configuration CORS n'est nécessaire. Un `fetch()` JavaScript vers l'URL en demanderait une sur le **bucket** (CORS du stockage, pas de l'API).
- Chaque gestionnaire de l'URL (proxy, historique du navigateur, logs d'un CDN) peut la voir : ne pas la mettre dans des journaux applicatifs.

## 6. Lancer et explorer

```bash
docker compose up -d --wait           # PostgreSQL, Redis, SeaweedFS
```

Dans `apps/api/.env` :

```
STORAGE_DRIVER=s3
S3_ENDPOINT=http://localhost:8333
S3_BUCKET=imageservice-dev
S3_ACCESS_KEY_ID=imageservice
S3_SECRET_ACCESS_KEY=imageservice-secret
```

Puis `npm run dev -w apps/api` (et `npm run worker -w apps/api`). Le bucket est créé au premier démarrage. Essai des URLs présignées :

```bash
curl -s localhost:3000/images/$IMG/url -H "Authorization: Bearer $TOKEN"     # → { url, expiresInSeconds, expiresAt }
curl -s -o copie.png "<url>"                                                  # SANS jeton : ça marche, jusqu'à l'expiration
``` Les identifiants viennent de
`docker/seaweedfs-s3.json` : **identifiants de développement, à ne jamais utiliser ailleurs**.

Voir les objets (SeaweedFS expose aussi son interface du *filer* sur le port 8888 **interne** ; sans l'exposer, on passe par l'API S3) :

```bash
# avec la CLI AWS (si installée)
AWS_ACCESS_KEY_ID=imageservice AWS_SECRET_ACCESS_KEY=imageservice-secret \
  aws --endpoint-url http://localhost:8333 s3 ls s3://imageservice-dev --recursive
```

Sans CLI AWS, un petit script Node avec `ListObjectsV2Command` fait l'affaire (voir `tests/helpers/test-s3.ts`).

## 7. Pièges rencontrés (à connaître)

1. **`No free volumes left` (HTTP 500 à la 1re écriture d'un nouveau bucket).** SeaweedFS réserve environ **7 « volumes » par bucket** ; avec
   `-volume.max=20` (valeur initiale), le 3e bucket ne pouvait plus rien écrire. Réglé avec `-volume.max=100` dans `docker-compose.yml`.
   Leçon : une erreur 500 « interne » d'un service tiers se diagnostique dans **les logs du service** (`docker compose logs seaweedfs`).
2. **« healthy » ne veut pas dire « prêt ».** Le healthcheck testait le *master* de SeaweedFS ; la passerelle S3 démarrait un peu après et
   l'API recevait `ECONNRESET`. Le healthcheck teste maintenant le port S3 (et `127.0.0.1`, car `localhost` se résout parfois en IPv6 `::1`),
   et l'application réessaie 10 fois au démarrage.
3. **Chaque bucket coûte des volumes** : ne pas créer un bucket par utilisateur.

## 8. À retenir

1. Le stockage objet = fichiers **par clé** dans un **bucket**, via une **API réseau standard** (S3).
2. Grâce au port `IFileStorage`, passer du disque à S3 n'a **changé aucun use case**.
3. Un **contrat de test** partagé garantit que deux implémentations sont interchangeables.
4. `If-None-Match: *` donne une écriture « une seule fois » **atomique** (pas de course entre `exists` et `put`).
5. Le stockage est **vital** : fail-closed au démarrage.
6. Avec S3, l'API et les workers partagent le même stockage, quelle que soit la machine.
7. Une **URL présignée** délègue le téléchargement au stockage : l'API autorise, calcule une signature locale, et ne voit plus passer les octets.
8. Une URL signée est une **permission** : courte durée, jamais journalisée, impossible à révoquer avant l'expiration.
